## 1. 透明代理红线专章（最高优先）

红线定义见 `[[transparent-proxy-redline]]`：`/v1/responses` 可读不可改数据体（账号/风控例外）；xAI 差异下沉仅限 `providers/xai` 内 raw Map surgery；不二次写枚举。

> **前提（勿再拿错尺子量 xAI）**：红线的「字节透传/不改数据体」约束的是 **OpenAI 路径**——Codex 客户端与 Codex 上游同一套 Responses wire，双向都不该改。**xAI 路径不适用**：Grok 与 Codex 是两套协议，xAI provider 请求侧必须翻译 Codex→Grok、响应侧必须把 Grok 流**重新合成**为 Responses 事件（`canonical.rs:214-244` 下发的是 `rewrite_stream_event` 转换后的合成 wire，不是 Grok 原始字节）。因此对 xAI 谈「字节透明」无意义。红线对 xAI 的真实约束只有两条：① 翻译要用**合法形态**（raw Map surgery + 未知字段随行，而非 `json!` 白名单重组）；② 不二次写枚举。以下先列唯一的 OpenAI 真红线项，再列 xAI 翻译形态项，最后单列已撤销的两条并说明为什么。

### ✅ P1（已修复 2026-07-26）　【唯一真红线】OpenAI WS 上游路径客户端字节被 serde_json 重打印

> **修复**：`provider.rs` 现对 HTTP SSE 与 WebSocket **两条**上游都启用 `with_raw_sse_passthrough()`。WS 的 body 由 reducer 以 `encode_sse_event(&event, raw)` 逐字节内嵌上游原文，`push_frames` 抽出的 `data` 即上游原始 JSON，下游按字节转发，不再经 serde 往返。回归测试 `websocket_raw_passthrough_should_preserve_upstream_number_bytes`（openai canonical）：上游 `1e3` 原样保留、未被重序列化为 `1000.0`。全量 clippy + 测试绿。
`backend/crates/providers/openai/src/provider.rs:822`

`with_raw_sse_passthrough()` 只在 `transport == HttpSse` 时启用（L822-824）；**WS 路径**（warmup、exact continuation、显式 `use_websocket`、continuation 快路径）走 `json_with_sse_metadata(raw_sse_frame=None)`，下游 `response.rs:48` 回退 `wire.data().to_string()` 重序列化。workspace serde_json 仅开 `preserve_order`、无 `arbitrary_precision`，Value 往返会改字节：`"1e3"→"1000.0"`、超 u64 整数降 f64 丢精度、`\uXXXX` 转义解开、重复键坍缩。2026-07-24 的 `ab8dffba` 只修了 HTTP 半边。**修法**：WS 衍生流同样启用 raw 透传（reducer 产出的 SSE 帧字节即上游原文）。

### ⟲ 重定性：xAI A3、A4 —— 非红线，但确认是相对 grok2api 基线的回归

> 初版把这两条挂在「透明代理红线」下并定 P0。经复读代码，**红线对 xAI 不适用**（xai 是翻译层，见本章前提）。随后对照用户指定的行为基线 **grok2api**（`/home/zyy/Codes/grok2api`，architecture.md 亦声明「xAI/Grok 行为以 grok2api 验证结果为基准」）逐行核实，结论：两条都不是红线违规，但**都是相对基线的真实回归**。

> grok2api 流式主循环 `streamConverter.handle`（`backend/internal/infra/provider/conversation/stream.go:195`）对上游异常**极度容忍，唯一会中断流的是向客户端写失败（断连）**：JSON 解析失败 `return nil`（L203）、字段缺失/空 delta 用 `_ = json.Unmarshal` 给零值照发、重复/乱序 index 不校验、已 finished 再来帧 `if c.finished { return nil }`（L196）、未知事件类型 switch `default: return nil`。错误事件 `error`/`response.failed` 经 `streamErrorValue`（stream.go:454）提取 `response.error`/`error`/`message` **原文转发给客户端**。

- **A3（`canonical.rs:255` 强 schema 校验断流）→ P1「翻译层健壮性回归」【✅ 已修复 2026-07-26】**：
  - **修复**：`decode` 循环现对**非终态内容事件**的 `Protocol` 类错误容忍——跳过该事件的 canonical 提取、wire 原样转发，流不断（对齐 grok2api）；`rewrite_stream_event` 转换失败改为跳过该帧而非断流。**终态事件（completed/incomplete）保留 fail-closed**（用量/计费校验失败仍断流，`decoder_should_fail_closed_for_non_integer_provider_cost` 仍绿）；真·上游错误（response.failed/error，非 Protocol 类别）仍按终态传播。回归测试 `decoder_should_tolerate_content_field_error_without_breaking_stream`：空 delta 不再断流、wire 仍转发、终态仍解出。
  - **纠正初版事实**：`decode_event` 的 `_ => Ok(())`（L291）**容忍未知事件类型且原样转发**（L239-243）。初版「未来所有非 `response.*` 事件族被吞掉/未知事件断流」的说法**错误、已删**。
  - **真实内核（基线背书）**：codex-proxy-rs 在 **grok2api 会容忍的正常上游变体**上断整条客户端流——空 delta（`required_text` L589）、重复 index（`add_content` L550）、已完成再来帧（L255）、kind 不符（L563）等，都会 `?` 上抛打断已开始的流，对 Codex 客户端表现为响应被截断。基线在这些场景全部 tolerate，因此这是**确认的回归**，非可接受的 fail-closed。
  - **修法**：把 `decode_event` 的 `Err(protocol_error_marker())` 路径降级为「跳过该事件的 canonical 提取、wire 原样转发」，仅客户端写失败/SSE 帧解码失败才断流——即对齐 grok2api 的容忍语义。
- **A4（上游 error 正文 redact）→ P2「错误透传回归」【✅ 已裁决并修复 2026-07-26，commit 2e0bee60】**：
  - **基线**：grok2api 把上游错误 `message`/`code` **原文转发**给客户端（`streamErrorValue`）。codex-proxy-rs 经 `redact_sensitive_context` 只留改写过的 code + 静态文案。故这是相对基线的回归。
  - **四方裁决依据（2026-07-26 补充核实）**：grok-build（xAI 官方 CLI）对结构化 JSON 错误**原文展示**（280/200 字符截断 + 内部服务名改写护栏）；codex（下游客户端）不仅展示 message，还**依赖 error.code 分致命/可重试、依赖 message 中 "try again in Ns" 定重试间隔**——redact 会把致命错误变成盲重试；grok2api 流内错误零脱敏转发，但其 fixture 证实 Grok 429 文案内嵌 **team UUID**（`console_test.go:271`），账号指纹风险真实存在。

## 2. 正确性与可用性

### 🟠 P1　CORS 配置任一 origin 即启动 panic
`backend/crates/gateway-api/src/lib.rs:153`（三路独立命中 + 最小复现实锤）

`!cors_allowed_origins.is_empty()` 时构造 `CorsLayer::new()...allow_headers(Any).allow_credentials(true)`。tower-http 0.7.0 `ensure_usable_cors_rules` 在 credentials=true 且 headers 为 wildcard 时 `assert!` panic；axum 0.8.9 `Router::layer` 立即求值，**panic 发生在 `initialize()` 内**。`deploy/config.example.yaml:49` 公开暴露该配置项，`validate_origin` 精细校验给了「配置可用」的错觉，实则填入任一合法 origin → 启动即 panic → Compose `restart: unless-stopped` 无限重启。测试只覆盖空数组。**修法**：`.allow_headers(Any)` 换显式白名单（`authorization`/`content-type`/`x-api-key`/`x-request-id`）或 `AllowHeaders::mirror_request()`，补非空 origin 装配测试。（本人已核 L140-155 属实。）

### 🟠 P1　管理员登录限流退化为全局单桶 —— 零成本管理面 DoS
`backend/crates/gateway-api/src/admin/auth.rs:217`

login handler 取 `Option<Extension<AdminLoginSource>>`，**全仓无任何中间件注入该 Extension**（grep 仅 3 处命中且均在 auth.rs 自身），故 `source` 恒为 `"unknown"`。限流键即 source（`use_case/auth.rs:141`、`redis/mod.rs:123`），所有访客失败落进同一个桶。任意未认证者对 `/api/admin/auth/login` 发 5 次错密码，15 分钟内合法管理员登录一律 429，每 15 分钟 5 请求即可无限续锁。测试（`tests/admin/auth.rs:54` 传 `"127.0.0.1"`）证明设计意图是按来源隔离。IP 本可得（`serve.rs:126` 已 `into_make_service_with_connect_info`）。**修法**：admin router 加中间件从 `ConnectInfo` 构造并 insert `AdminLoginSource`，unknown 与已知来源分桶。

### 🟠 P1　store 健康指标结构性恒 0 —— 仪表盘成功率永远 100%
`backend/crates/gateway-store/src/postgres/observability.rs:1657`

`request_metrics` 用 FILTER 算 `failure_count`/`cancelled`/`incomplete`/`caller_error_count`（L1656-1661），但 L1695 无条件追加 `push_completed_usage_fact_filter`（`and outcome='succeeded' and downstream_committed_at is not null and client_status_code between 200 and 399`，L2252）——WHERE 已把结局钉死为成功，**这些失败计数在集合上不可能命中**。`request_metric_series` 同样。下游 admin `service_failure_count = failure_count - caller_error_count` 推导 success_rate 与趋势 errors 序列。只要范围内有失败请求，Dashboard/Usage 成功率仍显示 100%、errors 曲线恒 0——健康观测完全失真。**修法**：把健康类计数从完成态过滤中解耦（用量/成本聚合保留过滤，请求结局计数改在未过滤子集上统计）。（本人已核 SQL 与 filter 函数属实。）

> ⚠️ 关联但**已推翻**：`diagnostics()` 与 `TrendPoint.success_rate` 两条「成功数虚高/分母不一致」发现经核验为 REFUTED——因为它们的数据源同样被完成态过滤器钉死，重算值与精确值**恒等**，不存在虚高。但这反过来印证：整套观测的失败维度都被这个 filter 结构性抹平了。

### gateway-core 执行链簇（coordinator.rs）
- 🟠 **P1　重试后终态把已持久化的 `sent` 发送屏障降级覆盖为 `not_sent`**（`coordinator.rs:984`）：`finish_provider_error` 用 `current_send_state()`，attempt1 已 `mark_send_state(Sent)` 但 current 被 take 不归还，attempt2 遇 `NoEligibleAccount` 时读回 `NotSent`，`finalize_model_request` 无条件覆盖该列 → 最终行 `send_state='not_sent'` 且 `status_code=429` 自相矛盾，破坏发送屏障审计事实。**修法**：维护请求级发送高水位，终态取 `max(高水位, error.send_state())`。
- 🟡 **P2　网关 10min deadline 到期被归因为 Provider Timeout 熔断失败**（L387）：长生成请求（>10min）属网关预算到期而非上游故障，却累积 provider 失败；多条长流同时到期可打开熔断，30s 内该 Provider 全部新请求被拒。`downstream_committed_at.is_some()` 时不应计入熔断。
- 🟡 **P2　同账号凭据恢复后 `required_account` 永久钉死**（L824）：401→OAuth 恢复→原账号重放，若再遇本可换号的错误（429/Sent），即使还有可调度账号和 32 次预算也立即终态。xAI `with_same_account_retry` 真实可触发。
- 🟢 **P3**：`reset_uncommitted_observations` 漏清 `provider_processing_ms`（L906，废弃 attempt 耗时泄漏进终态）；`finish_success` 无观测时凭空合成 `status_code=200`（L948）；`EmptyRoutingPlan` 被复用为内部不变量破坏错误且 attempts 封顶守卫不落终态（L440）。

### gateway-host 关停与自更新
- 🟠 **P1　`WorkerSupervisor::shutdown` 超时分支对已 join 的 handle 二次 await → tokio panic**（`workers/mod.rs:127`）：第一轮 timeout 内顺序 join，超时后对**全量** handle 再次 `await`。tokio 1.53.1 对已消费 handle 再 poll 会 `panic!("JoinHandle polled after completion")`。触发条件：任一 worker 30s 内未退出且它不是 BTreeMap 序第一个。现有测试恰好让挂死任务排第一而侥幸通过。**修法**：改用 `JoinSet` 或第一轮 join 成功即移出列表。
- 🟠 **P1　`drain_timeout` 无法约束 axum 优雅关闭**（`serve.rs:129`）：`with_graceful_shutdown` 无超时等待所有在飞连接，`wait_until_idle(drain_timeout)` 只在其返回后执行；而 HTTP SSE 响应体不观察 cancellation token。上游持续流式/慢客户端不读 body 时 `axum::serve` 永不返回，drain_timeout 形同虚设，后续 `workers.shutdown` 也无限期不执行，最终被 SIGKILL。**修法**：shutdown 信号后对 serve future 施加 `drain_timeout` 上界，或让 SSE unfold `select` on cancellation。

## 5. 多副本部署语义

architecture.md 宣称「单进程、可多副本部署」。逐机制核验结论：

**✅ 多副本安全**：`client_admission` 限流/并发完全下沉 Redis Lua 原子脚本且用 Redis TIME（RPM/并发精确不放大）；`provider_circuit`/session affinity/native continuation/credential cooldown 全部 Redis 原子下沉；RuntimeSnapshot 双通道收敛（Redis pub/sub + 5s Postgres revision 对账兜底，不一致窗口 ≈5s，fail-closed suspend）。

**⚠️ 多副本须知**（应写入部署文档）：
- 🟡 **P2　Worker leader lease 是「每周期互斥锁」而非跨周期 leader 选举**（`gateway-host/src/workers/mod.rs:521`）：`run_leased_cycle` 周期结束立即 `release_guard`，各副本定时器相位独立 → 无并发双跑，但「每 interval 恰好一次」失效，quota 同步/appcast 轮询/retention/目录刷新对上游/DB 调用**最高 N 倍**。**具体受害**：xAI 30 分钟配额最小刷新间隔靠进程内 `Mutex<BTreeMap>` 节流，副本交替获锁时各自 map 互不可见，节流被击穿 → 增加风控暴露。**修法**：有节流语义的任务把 `last_refresh_at` 下沉 Redis，或改真 leader（lease 跨周期持有 + 续租）。
- 🟡 **P2　自更新只替换处理请求的那个副本的本地二进制**（`system_update/swap.rs:11`）：多副本触发 update 后只有一台升级，其余停留旧版本（API 行为/迁移预期/前端 dist 不一致）；rollback 同理只回一台。**修法**：文档明确自更新仅限单副本，或检测到多 lease owner 时拒绝 update。
- 🟢 **P3**：ConnectionLocal WS 续写跨副本必然降级为全量 transcript 重放（应建议 LB 会话粘性）；副本被硬杀时在握 worker lease 依赖 15 分钟 TTL 兜底，期间全 fleet 同任务停摆；Catalog ETag daemon 每副本各一份无 lease，同一上游变更引发 N 倍全量抓取。

## 6. 安全加固（明文存储为有意设计，不计入）

**✅ 基线正确**：`/v1` client key 走常数时间比较（`constant_time_equal`）、四种失败收敛同一响应；归档解包拒绝 absolute/ParentDir/symlink/hardlink（无 zip-slip）；session token / admin key / client key / Argon2 salt 全用 `OsRng`；密码 Argon2；xAI 网络边界有 DNS rebinding 防护 + DoH 兜底；OIDC 验证 ES256 单算法 fail-closed。以下是缺口：

- 🟡 **P2　自更新无签名/attestation 验证，且二进制目录对运行用户可写**（`system_update/mod.rs:331`）：完整性根只有同源 checksums.txt（防损坏不防篡改）；发布侧其实已产出 `actions/attest` artifact attestation + keyless cosign 镜像签名（`release.yml:384/528`），**消费侧一个都没用**。信任根 = 「谁能往那个 GitHub Release 写 asset」（含 `CPR_UPDATE_REPOSITORY` 被改、CI 令牌失陷）；一旦成立即持久化 RCE（`replace_release_files` 覆盖运行中可执行文件 + `restart: unless-stopped`）。**修法**：verify_checksum 后加离线可验证签名校验（内置公钥验签的 checksums.txt，或校验 GitHub attestation 的 Sigstore 证书链绑定 repo/workflow identity），extract 前完成。
- 🟡 **P2　管理员密码首次创建后无法轮换，且无会话批量吊销**（`gateway-admin/src/lib.rs:234`）：`ensure_default_admin` 幂等创建（已存在哈希则静默不动、返回 bool 被丢弃），管理面 39 个路由无任何改密端点，`AuthStore` 无「按 admin_user_id 清全部 session」。口令泄露后产品内无路可走，必须直连 DB 改哈希；既有会话不可失效，攻击者 cookie 可用到 TTL（示例 1440min）到期。**修法**：加 `POST /api/admin/settings/password`（验旧密码 + 复用强度策略），成功后吊销该用户全部会话；`ensure_default_admin` 已存在哈希时 warn 一行。
- 🟢 **P3**：OpenAI 上游 `base_url` 只校验 scheme，允许明文 http 与任意内网主机（与 xAI 严格钉死不一致，`openai/config.rs:135`）；session cookie 无条件带 `Secure` 但无文档/开关说明必须 TLS（HTTP 部署会登录成功却拿不到会话，`admin/auth.rs:22`）；`security-scan.yml` 只覆盖依赖漏洞，缺 secret scanning，容器扫描不在 PR 上跑；release 资产选择兜底分支会挑中任意平台匹配资产且远端资产名直接当路径拼接（`release.rs:166`）。

### 🟠 P1　2.x → 3.x 一键更新砖机（含 4.0 前向风险）

已逐字复核：v2.5.3 的 `version_is_newer` 与现行**完全相同**（纯 semver、无 major gate）；两代资产契约逐字兼容（同一 `releases/latest` 端点、同一命名 `codex-proxy-rs_{ver}_{os}_{arch}.tar.gz`、同样 checksums.txt 与解包布局）。因此存活的 2.5.3 部署**今天就显示「3.0.10 可更新」**，点击后下载/校验/替换/重启全部成功，然后 3.x 二进制解析 2.x 布局 config.yaml 失败（`deny_unknown_fields` + 必填段）→ `InvalidDocument` 启动即死；即使手工迁移配置，2.x 库的 `0001`（不同 checksum）+`0002` 仍让 sqlx 拒绝启动（`postgres/mod.rs:43` `MIGRATOR.run` 失败即启动失败，**无 VersionMismatch 兜底**）。README/deploy/README/release notes 三处均无 clean-break 声明。docker 需 force-recreate 回退、binary 需手工恢复 `.backup`，rollback API 因进程起不来而不可用。**且 3.x updater 同样无门禁，4.0 clean break 时全部 3.x 部署复现。**

**修法**（三件）：① 现行 `detail_from_release`/`perform_update` 加 same-major 门禁（`latest.major != current.major` → `has_update=false` + `unsupported_reason`），为 4.0 兜底；② 每个 3.x GitHub Release body 首行加醒目警告（2.x UI 把 `release.body` 作为更新说明展示，是唯一能在点击前触达存量用户的通道）；③ README/deploy/README 明确 3.0 是 clean break。
