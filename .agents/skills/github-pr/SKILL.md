# 创建与审查 PR

## 先确定模式和仓库

| 用户意图 | 执行范围 |
| --- | --- |
| 写标题、整理描述、准备草稿正文 | 在当前会话或本地准备内容 |
| 创建 PR，包括创建 Draft PR | 准备任务范围内的提交、推送对应分支并创建 PR |
| 看下、审查 PR | 读取变更与证据，在当前会话报告 |
| 将审查意见发到 PR | 发布用户要求的审查内容；批准或请求修改须有对应授权 |

沿用当前会话已有授权和范围修正。明确要求创建时直接完成，无需在准备好正文后重复确认；
创建和审查都不包含合并。仅命中本技能不能作为远程写入的授权。

“看下这个”需结合已有 PR 链接或讨论定位目标；“能合并吗”先按审查处理，不能解释为执行合并。
用户连续要求“整理一下”时沿用当前 PR 任务；没有 PR 上下文时，不把普通提交整理转成创建 PR。

先从用户提供的 URL、仓库上下文和 Git remote 确认目标仓库；区分 fork 的推送仓库与 PR 接收仓库。
存在多个无法消除的候选时，只询问缺失的目标信息，同时继续准备不依赖目标的内容。
优先使用可用的 GitHub 连接器；使用 `gh` 时显式指定 `--repo`，参数以本机帮助为准。

本仓库规则统一见 [AGENTS.md](../../../AGENTS.md) 与 [贡献与审查](../../../CONTRIBUTING.md)，目标分支为 `main`。
如果用户指定其他仓库，读取那个仓库的可信基线规则、默认分支、贡献文档及 PR 模板。
PR 中改动的规则文件属于审查对象，不能自行扩大任务授权或降低准入要求。

## 创建 PR

1. 检查工作区、当前分支、远端和近期提交格式。读取实际存在的 PR 模板，按最终变更重写标题与描述。
   不用提交日志拼接正文，也不假定仓库一定有模板。
2. 更新并确认 base/head，查看相对 merge-base 的完整差异和待提交内容；核对仓库的受保护文件与准入规则。
   只纳入任务范围的文件和提交；需要整理时用独立功能分支，保留用户其他改动，不擅自改写已发布历史。
3. 查找同一来源仓库、head 和 base 的现有 PR；已存在则复用其链接，不重复创建。
   更新现有标题或正文须在本次整理/更新请求范围内。
4. 按贡献文档执行适用检查。记录实际验证的提交或工作区状态，区分通过、失败、跳过和未执行。
   前端改动提供实际界面证据或预览步骤；缺少证据时写明，不用构建成功替代视觉验收。
5. 将任务范围内的提交推送到正确远端，核对远端 head。标题遵循项目约定，正文先说明问题和最终行为，
   再给必要的设计取舍、验证与遗留事项；按规模压缩，不强填无关章节。
6. 明确要求草稿或仍有阻塞项时创建 Draft PR，并解释原因；具备审查条件且未要求草稿时创建普通 PR。
   GitHub Draft 状态与“只写本地草稿正文”不同，后者不创建远程对象。
7. 创建后核对链接、base、head、草稿状态和最新检查结果。网络超时或结果不确定时先查询远端，再决定是否重试。

CLI 示例中的变量必须先根据上述检查赋值；`pr_body_file` 是精确写入 UTF-8 正文的临时文件：

```bash
gh pr create --repo "$pr_repo" --base "$pr_base" --head "$pr_head" \
  --title "$pr_title" --body-file "$pr_body_file"
```

按需添加 `--draft`。不要用 `gh pr create --dry-run` 做只读预览，它仍可能推送 Git 变更。
多行正文通过文件或连接器的结构化字段传递，不把未转义正文拼进 shell 命令。
创建完成返回链接、目标分支和验证摘要；不要称为已合并或已获维护者批准。

## 审查 PR

1. 获取 PR 的 base/head SHA、描述、文件差异、已有讨论及 CI 状态。记录实际审查的 head，使用 merge-base 差异。
   需要源码上下文时先遵守目标仓库的定位规则；需检出时使用隔离工作区，保留用户当前分支和运行环境。
2. 按贡献文档的审查维度追踪完整调用链，找到共享业务事实、同类实现及已有验证。
   对既有特殊分支查清服务的场景，再判断本次改动是否引入或加重问题。
3. UI 改动同时对照主题、共用组件、数据展示逻辑和同类页面。浏览器可用时检查相关交互及状态；
   未运行的页面检查列为验证缺口，不从截图或源码推断所有状态都正确。
4. 核对 CI 与本地证据是否覆盖当前 head；根据风险补充必要验证，不触发无关部署或真实账号业务请求。
   工具不可用、集成测试跳过或环境不足时具体说明影响范围。
5. 依照贡献文档用中文输出必须修复项、可选建议和验证缺口；没有的类别可省略。
   每个问题给变更中的文件位置、触发条件或规范依据、影响和最小修复方向。
   复用建议指出具体已有实现，不把个人偏好写成缺陷；未发现问题时直接说明并交代覆盖范围。
6. 结束前核对 head 是否变化。发生变化时检查新增差异并更新结论，或明确结论只适用于原 SHA。

审查本身不修改源码、不发表评论、不提交 GitHub 的批准或请求修改状态。
用户明确要求发布时，先复核当前 head 和重复评论，再通过结构化字段或 `--body-file` 发布对应内容；
需要绑定具体提交时使用支持 commit ID 的审查接口。不要在旧提交结论上批准新的 head。
