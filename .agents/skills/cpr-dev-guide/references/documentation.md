# 文档检查

仅在准备修改文档或最终差异含文档时读取，职责与行文依据是 [文档职责与更新条件](../../../../CONTRIBUTING.md#文档职责与更新条件)，只读该节

## 写之前

先明确这段内容服务谁、解决哪个当前使用或维护问题、属于哪个现有章节，再决定详略

接口保留调用合同，架构保留职责与不变量，部署保留操作与排障；同一事实只在所属位置完整说明，其他位置链接

常规文档在原章节修订，不追加本次变更小节，不为了“同步文档”补写修复总结

内部重构、实现经过、前后对比、验证结果应留在 PR、Issue 或任务报告

## 逐段验收

检查工作区和暂存区中本任务的最终文档差异，按内容用途处理，不只搜索关键词：

| 段落回答的问题 | 处理 |
| --- | --- |
| 现在如何使用、配置或理解结果 | 保留当前事实与必要边界，放回所属章节 |
| 谁负责状态、事务、资源和失败处理 | 放入所属架构章节，避免在 API 或部署文档复述实现 |
| 这次做了什么、以前怎样、为什么这样修、跑过哪些测试 | 移入 PR、Issue 或任务报告，不以换成现在时的方式留在常规文档 |
| 特定配置或数据状态下如何升级、恢复 | 写明适用条件、操作及限制，删除演变过程 |
| 别处已完整说明的事实 | 合并或改为必要摘要与链接 |

脱离提交日期、Issue 和本次任务背景后，读者仍应能独立理解正文

业务中的请求历史、审计记录、旧数据兼容与回滚操作是当前功能，不能因含“历史”“旧”等词而删除

## 交付检查

- 检查新段落的必要性、归属、重复与当前状态表达，发现变更叙述先改完再交付
- 标题、短列表、表格和独立短段通常不加句号，长段按主题拆分，命令与字段保持准确
- 检查相对链接、章节锚点、表格与命令示例，`git diff --check` 或构建通过不能代替内容审查
- 报告实际覆盖和缺口即可，不把检查记录写进常规文档

只有明确的发布说明任务才进入 `cpr-release`，`release/notes.md` 用于该次发行，不向 README、API、架构或部署文档复制版本变化列表
